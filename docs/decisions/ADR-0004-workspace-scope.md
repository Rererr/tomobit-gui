# ADR-0004: Tomoが働く場所 — 作業ディレクトリと読み取り先

- Status: **Accepted**（2026-07-25 起草・実装。同日、所有者の指摘
  「ClaudeCode だけに依存している点・次回チャットからじゃないと動かない点」を受けて
  Decision 2/3 を改訂 — 本体 ADR-0047 で口を作り直し、Provider 非依存かつ走行中の
  チャットに届く形にした）
- Date: 2026-07-25
- 関連: [ADR-0001](ADR-0001-gui-architecture.md)（Decision 2: 会話の経路 = `tomobit chat` 子プロセス /
  Decision 4: 好みの喋り方 = Provider起動引数への注入・反映境界 = セッション境界）,
  本体 [ADR-0021](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0021-wiring-is-not-experience.md)（配線は経験ではない）,
  本体 [ADR-0043](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0043-auto-by-default.md)（Provider選択）

---

## Context

端末で `tomobit chat` を打つ人は、打った場所がそのまま Tomo の作業場所になる。
Provider（claude CLI 等）は tomobit プロセスの cwd を継承するからで、
「このリポジトリで話したい」は `cd` で表明できていた。

GUI にはその `cd` が無い。子プロセスは GUI プロセスの cwd を継承するので、
Finder/Launchpad 起動なら `/`、端末起動なら端末の cwd —— **人が意図していない場所**で
Tomo が働く。ファイルを読ませたい相手（プロジェクト）と、Tomo が実際に立っている場所が
食い違うのに、画面のどこにもそれが出ていない。

作業場所は「送信のたびに効く文脈」であって、腰を据えて開く設定ではない。
各種LLMのチャットGUIが入力欄の周りにモデルや参照先を添えるのと同じ位置に置くのが
実態に合う。

---

## Decision 1: 作業ディレクトリ = chat 子プロセスの `cmd.Dir`

`tomobit chat` を起動するとき、設定された作業ディレクトリを子プロセスの
cwd として与える。本体もProviderもそれを継承する（本体が cwd に依存する状態を
持たないことは実装で確認 — 台帳・設定・顔窓ロックはすべて `~/.tomobit` 基準）。

- GUI プロセス自身は `chdir` しない: 顔窓・`status`・`forget` など他の子プロセスや
  相対パス解決に副作用を撒くのを避ける。作業場所は**チャットの子プロセスにだけ**渡す
- 未設定＝従来どおりの継承（GUI の起動ディレクトリ）。設定を入れるまで挙動は変わらない
- 起動前に存在を確認し、無ければ「作業ディレクトリが見つからない」と名指しで返す。
  `cmd.Dir` に消えたパスを渡した exec の生エラーは、人には原因が読めない

## Decision 2: 読み取り先は本体の `/add-dir` で渡す（2026-07-25 改訂）

**初版**: `TOMOBIT_CLAUDE_ARGS_APPEND` に `--add-dir <path>` を積む。好みの喋り方
（ADR-0001 Decision 4）と同じ口に載せ、GUI は新しい注入経路を作らない —— そして
「この口は claude 固有だから codex では効かない」という非対称を、正直に UI へ書いて
受け入れる、とした。

**改訂**: その非対称は受け入れるべきではなかった。所有者の指摘（2026-07-25:
「ClaudeCode だけに依存している点」）のとおり、Provider を選べる（本体 ADR-0043）
のに設定の効き目が Provider によって変わるのは、選択を無意味にする不具合である。
非対称の出どころは GUI ではなく**本体に口が無かったこと**なので、本体側で解いた:

- 本体 [ADR-0047](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0047-workspace-is-wiring.md):
  `executor.Request` に `WorkDir`/`AddDirs` を持たせ、各 Adapter が自分の CLI 語彙へ
  翻訳する（claude も codex も `--add-dir` を持つ — 実測で確認）
- GUI は claude 固有の env をやめ、本体のコマンド `/add-dir` で宣言する

「本体が持たない語彙を GUI が先取りしない」という初版の判断は維持している。
変えたのは**本体に語彙を作った**ことで、GUI が codex を知るようにしたのではない。

## Decision 3: 反映は走行中のチャットにも届く（2026-07-25 改訂）

**初版**: cwd も env もプロセス起動時に固定されるので、反映は「次のチャット
（New chat で区切った後）から」。

**改訂**: プロセス境界を待たせるのは過剰だった。本体 ADR-0047 Decision 4 の
`/cd`・`/add-dir` に宣言を送ることで、**走行中のプロセスのまま**新しい場所が効く。
`SetWorkspace` は保存と同時にその宣言を書き、GUI はプロセスを再起動しない。

境界の規律は本体のものをそのまま尊重する: タスクの途中なら本体が
「タスクの途中では替えられない — /new で区切ってから」と答え、その返事は view
ストリームでチャット面に出る。**GUI はこの規律を先回りして語らない** —— 本体の
語彙を複製すると、本体が規律を変えたとき GUI だけが古い説明を続ける。

宣言は**全置換**で組む（`/cd` → `/add-dir clear` → 各 `/add-dir`）。GUI は一覧
まるごとを持っているので、差分を送るより画面と本体がズレようがない。
ただし「作業ディレクトリを未設定へ戻す」宣言は無い（`/cd` にその語彙が無い）—
そのときは何も送らず、次のプロセス起動で継承に戻る。

## Decision 4: 置き場は入力の器の中 — ログと入力欄の間

設定ペインではなくチャット面の底、ログと入力欄の間に置く。

- 作業場所は「今どこで働いているか」の**状態表示**であり、次の送信に効く文脈である。
  見えない場所に畳むと、端末の `cd` が持っていた「打つ前に見えている」性質を失う
- 保存先は `~/.tomobit/gui.json`（配線であって経験ではない — 本体 ADR-0021）。
  台帳には何も書かない
- 選択は OS のフォルダ選択ダイアログ（Wails runtime）。パスの手入力欄は持たない —
  存在しないパス・打ち間違いという検証の面倒を、初めから作らない

## Decision 5: 消えた読み取り先は落として言う。会話は止めない

起動時に読み取り先の存在を確認し、消えていたものは宣言から落とし、
診断を1行 stderr 面へ出す。作業ディレクトリ（Decision 1）とは扱いが違う:

- 作業ディレクトリが無いのは「立つ場所が無い」であり、起動を止めて名指しで返す
- 読み取り先が1つ消えたのは劣化であって不能ではない。会話ごと止めるのは過剰。
  ただし黙って落とすと「読めるはず」の誤解が残るので、必ず言う（握り潰さない）

---

## Consequences

- GUI から起動した Tomo が、人の意図した場所で働くようになる。端末の `cd` に
  相当する表明手段を、GUI が初めて持つ
- 作業ディレクトリは Provider の権限範囲そのものになる（claude は cwd 配下を
  読み書きする）。設定 UI は「どこを開けるか」の宣言であり、軽い見た目のわりに
  効き目は重い —— だからこそ現在地を常時見せる位置に置く
- 設定の保存口が2つ（設定ペイン／作業バー）になった。どちらも `gui.json` を
  書くため、片方が持つ古いコピーで他方の変更を消しうる。フロントエンドは App が
  保持する1つの設定を単一の真実とし、さらに作業バーの `SetWorkspace` は Go 側で
  ディスクの現行を読み直してから2項目だけ差し替える（画面の写しが古くても壊れない）
- 端末で `tomobit chat` を使う人も、本体 ADR-0047 の `/cd`・`/add-dir` を同じ
  規律で使えるようになった。GUI のための口が端末にも効く形で入っている

### Open Question

- 作業ディレクトリの履歴（最近使った場所の切り替え）は持たない。1つで足りるかは
  使ってから決める。プロジェクトごとの記憶が要るなら、それは gui.json の配線でなく
  台帳側の話になりうる（Tomo が「あのときの場所」を覚えている、の意味論）

## 追記（2026-07-26）: ADR-0009 による Decision 1/2 の改訂 — 働く場所は窓ごとになる

上の Open Question は「1つで足りるか」と書いたが、**足りなかった**。
[ADR-0009](ADR-0009-four-panes.md)（会話面の四分割）が「Aリポのタスクα」「Aリポの
タスクβ」「Bリポの作業」を同時に持つ形を認めたので、`working_dir` と `read_dirs` を
`gui.json` のグローバルな1組として持つ前提が成り立たなくなった。

- `gui.json` のスキーマを窓（pane）の配列へ拡張し、窓ごとに働く場所を持つ。
  窓の構成（何窓・どの場所）は次回起動時に復元する
- **Decision 3（反映は走行中のチャットにも届く）は不変** — 宣言はその窓の chat に
  だけ飛ぶ
- **Decision 4（置き場は入力の器の中）も不変** — 作業バーが窓の数だけ立つ
- **Decision 5（消えた読み取り先は落として言う）も不変**

答えは「履歴を持つ」ではなく「**同時に複数持つ**」だった。ただし Open Question が
示唆した台帳側の意味論（Tomo が場所を覚えている）は、依然として別の論点である。

なお、同じ場所で働く窓が2つ立ちうることは GUI が**判断せずに事実として言う**
（ADR-0009 Decision 6）。作業ツリーの衝突そのものは本体
[ADR-0050](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0050-workspace-isolation-protocol.md)
（作業場の隔離）が引き受ける。
