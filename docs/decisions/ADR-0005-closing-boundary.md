# ADR-0005: 窓を閉じる前の締め — 待たせるなら、答えられる形で

## Context

窓の×を押すと、窓はすぐには閉じない。数秒〜十数秒のあいだ固まってから消える。

原因は `app.go shutdown`: chat 子プロセスの stdin を閉じ（端末の Ctrl-D にあたる）、
プロセスの終了を最大15秒（`chatShutdownGrace`）待つ。その15秒のあいだ本体は
**境界の器官を走らせている** —— Feedback（今回、どうだった?）→ 知覚 → Tomoの質問
→ 鏡。EOF なので Feedback は「無信号」として素通りし、知覚だけが黙って走る。

つまり:

- **Tomo は毎回、締めに何かを訊こうとしている**。ADR-0035 は器官が pipe にも
  届くようにしたのに、閉窓の経路だけは EOF で全部を素通りさせていた
- **人には「重い」としか見えない**。凍った窓の裏で何が起きているかは、
  この GUI のどこにも書かれていない
- 記帳される Feedback は常に空。GUI から閉じた会話は、**一度も評価されないまま**
  台帳に積まれ続ける（ADR-0006 Decision 4 が集めたかった信号が構造的に欠ける）

端末なら Ctrl-D の後に質問が出て、その場で答えられる。GUI にはその席が無かった。

---

## Decision 1: ×は閉窓を差し止め、New chat と同じ区切りを走らせる

Wails の `OnBeforeClose` で閉窓を止める（`app.go beforeClose`）。

- 生きている chat があれば `/exit` を送る —— **New chat が送るのと同じ行**。
  区切りの意味論は本体のもののままで、GUI は新しい締め方を発明しない
- chat が居なければ差し止めない。区切る相手が無いのに窓が閉じないのは、
  ただのバグに見える
- `/exit` すら送れない（既に死んだ chat）なら差し止めない。走らない区切りに
  閉窓を人質に取らせない
- **二度目の×は差し止めない**。締めから降りる意思は人のもので、GUI が
  「まだ答えていないから」と延長する筋合いは無い

## Decision 2: 締めの質問はモーダルのボタンにする。選択肢は本体の行から読む

`app:closing` を受けた画面は、締めのあいだだけモーダル（`ClosingDialog`）を出す。
`await` 付きの note がそこへ問いとして流れ、ボタン1つ＝端末で打つ1行になる。

**選択肢の一覧を GUI は持たない**。届いた行の角括弧をその場で読む
（`boundaryChoices.ts`）:

```
今回、どうだった? [1=文句なし / 2=まあまあ（手を焼いた） / 3=だめだった / Enter=まだ言えない]
                  └─────────────── ここを4つのボタンにする ───────────────┘
```

- 語彙を GUI 側に写せば、本体が選択肢を足した日に GUI が黙って古い口を出し続ける
  （`forget.go` の「検証者を増やさない」と同じ理由）。同じ規則で Feedback・
  Tomoの質問・鏡の3器官がそのまま賄える
- 角括弧が読めない行（自由記述を待つ器官）はテキスト欄で受ける。**ボタンが
  作れないという理由で答える口ごと消える**のを避ける
- `Enter=` の選択肢は空文字の送信 —— 本体の「無信号」経路そのもの。押し間違いで
  台帳に信号が入らないよう、他の選択肢と見た目の重さを分ける
- 締めの行はチャット面のログにも今までどおり積む。モーダルは締めの間だけの器で、
  会話の記録ではない

## Decision 3: 締めが終わったら閉じる。降りる道は1つだけ置く

- `chat:exit` が届いた時点で待つものは無い。人の意思（×を押した）どおり閉じる
  （画面から `QuitNow`）。異常終了でも同じ —— 待ち続ける相手がもう居ない
- 「待たずに閉じる」を1つ置く（`AbandonBoundary`）。押されたら `shutdown` は
  猶予を捨てて即座に回収する。**猶予を残したまま閉じると、答えないと決めた後に
  15秒固まるという、この ADR が直したはずの症状がそのまま戻る**
- 失うものは文言に書く: 知覚は途中で止まり、そのセッションの `task.finished` は
  記帳されない（猶予切れの Kill で従来から起きていたのと同じ結末）。
  積み残しは後から `tomobit perceive` が消化する
- Esc では閉じない。取り消せない選択（知覚を捨てる）をキー1つの誤爆から遠ざける

---

## 却下した対案

- **×で即座に kill する** → 「重くない」代わりに、締めの器官が毎回途中で死ぬ。
  速さのために台帳を痩せさせる取引で、VISION の逆を向く
- **締めを黙って背景で走らせ、窓だけ先に消す** → 子プロセスのパイプは親の終了で
  閉じ、知覚の途中で書き込みが壊れうる。「終わったことにする」のは
  正直さの問題でもある
- **質問をチャット面のまま答えさせ、窓は開けておく** → ×を押した人に
  「まだ閉じません」と言うだけで、何を待っているかは相変わらず画面に無い。
  モーダルは待ちの理由をそれ自体で説明する
- **New chat の質問もモーダルにする** → New chat は会話の続きであり、締めの尾部は
  そのままログに流れるのが読みやすい。モーダルは「窓が閉じない理由」を説明する
  ためのもので、会話中の器官まで前に出す理由は無い

## Consequences

- `main.go` に `OnBeforeClose`。`app.go` に `beforeClose` / `QuitNow` /
  `AbandonBoundary` と `closingBoundary` / `abandonBoundary`
- `shutdown` の猶予は「待たずに閉じる」経路でだけ飛ばす。通常経路では
  `beforeClose` が先に区切りを済ませているので、`shutdown` 到達時に子は既に居ない
- テスト（`closing_test.go`）が固定するのは、差し止める条件・送る行・二度目の×・
  送信失敗時に人質を取らないこと・「待たずに閉じる」が猶予を待たないこと
- **GUI から閉じた会話にも Feedback が記帳されるようになる**。これまで空だった
  `task.finished` の payload に信号が入り、台帳の質が上がる
