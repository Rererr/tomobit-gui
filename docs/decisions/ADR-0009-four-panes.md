## Context

人は同時に複数のことをやる。「Aリポジトリのタスクα」を走らせながら「Aリポジトリの
タスクβ」も進め、ついでに「Bリポジトリの作業」も動かしたい。今のGUIは会話面を
1つしか持たないので、この形が取れない。

本体側には、この禁止に理由が書いてある。ADR-0028 Decision 4、human サブタスクの扱い:

> 独立宣言が順序の入替を合法にし、**端末が1本という物理が human の並走を禁じる** —
> 判断ではなく制約の写像

禁じていたのは判断ではなく**制約の写像**だと、ADR自身が宣言している。GUIはその物理を
持たない。制約が無いのに禁止だけを引き継げば、それは写像ではなく Rule になる。

一方で、素朴に4つ並べると2つのものが壊れる:

- **作業ツリーの共有**: 「Aリポのα」と「Aリポのβ」は同じディレクトリを2つの
  Providerが同時に書く。汚染された実行は `provider.error` として台帳に載り、
  Providerの Beta が下がる。Providerは悪くないのに、経験という資産に泥が入る
- **Tomoの同一性**: 窓が4つあると「Tomoが4匹いる」ように見えてしまう

前者は本体 [ADR-0050](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0050-workspace-isolation-protocol.md)（作業場の隔離）が引き受ける。
本ADRはそれを前提にしたうえで、後者に答える。

## Decision 1: Tomoは一匹、台帳はひとつ、窓は腕

窓を増やしても Tomo は増えない。**窓ごとにDBを選ばせない。**

これは好みではなく、他の決定から導かれる帰結である:

- 本体 ADR-0019 が「相棒らしさ・感情・個性はすべて**台帳のView**」と決めた
- 本体 ADR-0008 が「姿はView」「姿が嘘をつける相棒は相棒ではない」と決めた
- 本体 ADR-0039 / ADR-0048 で stage・mood・speak・sprite はすべて導出View

つまり **Tomoの同一性 = 台帳の同一性**である。台帳が1つなら、Tomoは論理的に1匹しか
ありえない。2匹にする方法が設計上どこにも無い。そして本体 ADR-0018 は
「Tomobitは取り替えられてもよい。しかしTomobitを育てた経験は、誰にも持っていかれない」
と書いた。**Tomoの本体は台帳そのもの**なので、「窓ごとにTomo」は「窓ごとに台帳」と
同義になり、経験主権の第一文と正面から衝突する。

明示的に禁止を書く理由がある。[facelock](https://github.com/Rererr/tomobit/blob/main/internal/facelock/facelock.go) には
既にこう書かれている — 「the mascot is one per machine (ADR-0025 Decision 2),
**not one per DB**」。顔は機械に1つ、台帳は複数ありうる、という非対称が既にある。
放置すれば、四分割GUIが**Tomoを複数にできる唯一の口**になってしまう。

分割するもの / しないものの線:

```text
分割しない（Tomo一匹の側）      分割する（仕事の側）
ヘッダ（stage / mood / speak）  会話ログ
成長開示（growth）              入力欄
サイドバーの姿（sprite）        待ちの表示（ADR-0008）
Usage / 残量                    働く場所（ADR-0004）
セッション一覧・メモリペイン    締めのダイアログ（ADR-0005）
```

サイドバーは分割しない。ADR-0006 が「姿と利用状況は開くものではない」と置いた常設
Viewは、Tomo一匹に属するものだからである。

却下した対案:

- **窓ごとにDBを選べるようにする**: 上記のとおり Tomo が複数になる。「複数のTomoを
  育てる」は別ADRの論点であって、レイアウトの決定に紛れ込ませてよいものではない
- **窓ごとにヘッダを出す**: 同じ導出Viewが4つ並ぶだけ。同じ値なら1つでよく、
  違う値が出るなら台帳が複数あることになる（禁止済み）

## Decision 2: 1窓 = 1 chat プロセス = 1セッション。起動は最初の送信まで遅らせる

ADR-0001 Decision 2（会話の経路 = `tomobit chat` 子プロセス）と Decision 4 追記
（反映境界 = セッション境界 = プロセス境界）は不変で、**窓ごとに成立する**。

- 窓の上限は4（画面の物理。1・2・3・4分割）
- **窓を開いてもプロセスは起動しない**。今と同じく最初の送信で起動する
  （`ensureProcLocked`）。空の窓が quota も残量も食わないのは、遅延起動の副産物として
  そのまま効く
- 窓を閉じる = その窓のセッションを区切る（Decision 4）
- 各窓の `/new`・`/exit`・境界の器官はすべて窓の中で完結する。窓Aの区切りが窓Bの
  会話に触ることはない

却下した対案:

- **1プロセスを4窓で共有する**（多重化した1本のchat）: 本体は1プロセス1タスクで、
  `experiences.provider` は1セッション1つ（本体 ADR-0022 Decision 5）。多重化すれば
  「どのProviderがこの結果を出したか」が壊れる。**台帳の形が拒否している**
- **窓を開いた瞬間に起動**: 使わない窓が Provider の枠を握る

## Decision 3: 働く場所は窓ごと — ADR-0004 を「gui.json に1つ」から改訂する

ADR-0004 は `working_dir` と `read_dirs` を `gui.json` のグローバルな1組として置いた。
本ADRはこれを**窓ごと**に改める。「Aリポのα」「Bリポの作業」が同時に立つのだから、
働く場所が1つしか無いという前提はもう成り立たない。

- `gui.json` のスキーマを拡張し、窓（pane）の配列として持つ。窓の構成（何窓・
  どの場所）は次回起動時に復元する
- ADR-0004 Decision 4（置き場は入力の器の中 — ログと入力欄の間）は不変。作業バーが
  窓の数だけ立つ
- ADR-0004 Decision 3（反映は走行中のチャットにも届く）も不変。宣言はその窓の
  chat にだけ飛ぶ
- ADR-0007 の実行ボタンが使う作業ディレクトリも、その窓のものになる。
  `RunCommandProvider` は今 `#app` の一番外側で1度だけ配っている（[App.tsx:595](../../frontend/src/App.tsx:595)）が、
  窓のスコープへ下げる

## Decision 4: 締めは窓の中で完結する — ADR-0005 を窓の数だけ増やす

ADR-0005 は「×は閉窓を差し止め、New chat と同じ区切りを走らせる」と決めた。窓が
複数になると、締めも複数になる。

- **1窓を閉じる**: その窓の中にダイアログが出る。窓の外（他の窓・サイドバー）は
  動き続ける。当時の `ClosingDialog` は
  `#app` 直下（[App.tsx](../../frontend/src/App.tsx)）だったので、窓のスコープへ下げる
- **アプリごと閉じる**: 生きている窓すべてに `/exit` を送り、**全部の締めが終わるまで
  閉じない**。ダイアログは窓ごとに、同時に立つ。ADR-0005 の
  「降りる道は『待たずに閉じる』1つ」も窓ごと — ただしアプリの×に対しては
  「全部の締めを待たずに閉じる」を1つ用意する（二度目の×は差し止めない、という
  ADR-0005 の規律をそのまま伸ばす）
- **Feedback は窓の数だけ聞く。これは摩擦ではない。** 本体 ADR-0028 Decision 5 が
  サブタスク個別のFeedbackを廃したのは「**機械が勝手に分けた**ものに人が何度も
  答えるのはおかしい」からだった。窓は人が明示的に開いたもので、中身も別の仕事である。
  分けたのが人なら、答えるのも人でよい

> **追記（2026-07-29）**: アプリごと閉じる場面の見せ方は
> [ADR-0012](ADR-0012-one-sheet-for-app-closing.md) が置き換えた — 窓ごとに
> ダイアログが同時に立つのではなく、App 直下の1枚に全窓の締めを縦に並べる。
> 「待たずに閉じる」も窓ごとではなく1枚に1つで、窓単位のスキップは質問の
> 「まだ言えない」（空送信）が受け持つ。Feedback を窓の数だけ聞くこと自体は
> 変わらない。

## Decision 5: Tomo一匹の資源は、窓が食い合う

窓は増えても Tomo は1匹なので、Tomo に属する資源は窓の数だけ増えない。増やせば
台帳が嘘をつく。

- **好奇心予算（本体 ADR-0007 の BudgetWindow）は人ごと**。予算の意味は「Tomoが人に
  質問していい回数」で、人は1人しかいない。ただし同時に区切られた窓のうち1つだけが
  質問できて残りが無言になるのは体験として不可解なので、**質問はキューに積んで順に
  出す**（予算そのものは増やさない）
- **境界の知覚（ローカルOllama）は逐次化する**。3窓が同時に区切られれば
  qwen3:8b が3本同時に飛ぶ。本体 ADR-0041 が out-of-order 知覚を既に扱っているので、
  順序を落としても台帳は嘘をつかない。**これは思想ではなく実測の話**で、
  並列度は実機で測ってから決める
- **並走幅（本体 ADR-0028 の群並走・初期上限3）は machine-wide で見る**。
  4窓 × 3本 = 12プロセスが、1本ずつのゲートを通って同時に立ちうる。
  [presence](https://github.com/Rererr/tomobit/blob/main/internal/presence/presence.go) が
  機械上の生存セッションを数えられるので、並走ゲートの文言に
  「（現在ほかの窓で N 本走行中）」を足す。**判断はしない — 数を言うだけ**
- **quota / 残量（本体 ADR-0044・ADR-0049）には本ADRでは触れない**。ただし4窓は
  quota観測の意味を変える（「今空いている方」ではなく「今この瞬間、自分の他の窓が
  使っていない方」になる）。別ADRの論点として残す

## Decision 6: 同じ場所で働く窓があることは、判断せずに事実として言う

本体 ADR-0050 が作業場の隔離をProviderに委ねても、`isolated: false` は正常な返答として
起こりうる（VCS無し・submodule・LFS）。そのとき2つの窓は本当に同じツリーを共有する。

GUIは止めない。禁止も警告のモーダルも出さない。**観測した事実を1行言うだけ**にする:

```text
この窓は、もう1つの窓と同じ場所で働いている
```

これは既存の流儀そのままである — [App.tsx:539](../../frontend/src/App.tsx:539) の
「働く場所を保存した — 今のタスクには効かない」も、ADR-0008 の待ちの帯も、同じ規律に
立っている: **食い違いを黙って作らない**。判断はしないが、観測は言う。

却下した対案:

- **同じ `working_dir` の窓を2つ開けないようにする**: 判断の座席をGUIに作る。
  隔離が効いていれば安全な組み合わせまで禁じることになる
- **何も言わない**: 事故が起きるまで人は共有に気づかない。台帳に泥が入ってから
  分かるのでは遅い

## Consequences

- **フロントの状態を窓ごとへ切り出す**: 今 [App.tsx](../../frontend/src/App.tsx) に
  直に置かれている `messages` / `openTurnIdRef` / `boundaryRef` / `closingRef` /
  `activityRef` / `pendingDecidedRef` / `pendingBlocksRef` はすべて1ストリーム前提。
  `useChatSession(paneId)` へ抽出する。窓が1つのままでも振る舞いが変わらないことが、
  この抽出の完了条件になる
- **Go 側の多重化**: [app.go](../../app.go) の `proc *chatProc` をキー付きへ。
  `ensureProcLocked` / `sendProc` / `invalidateProc` / `EndTask` / `beforeClose` /
  `shutdown` がすべて「1本」を前提にしている
- **イベントに窓の識別子を載せる**: `chat:out` / `chat:view` / `chat:exit`
  （[chat.go:26](../../chat.go:26)）は今どれも宛先を持たない。payload に窓の id を足す
  （イベント名を窓ごとに分けるのではなく — 購読側が窓の数だけ購読を張り替える形は
  避ける）
- **レイアウト**: [App.css:384](../../frontend/src/App.css:384) の `.main-pane` を
  flex column から grid へ。[App.tsx:640](../../frontend/src/App.tsx:640) の
  `display: contents`（1枠を隠す/見せるための書き方）は grid セルにできないので捨てる。
  `.chat-pane` 側は `position: relative` + flex column で既にセルに収まる形になっている
- **スクロールバック**（ADR-0003）のファイル名は `<sid>.ndjson`
  （[scrollback.go:47](../../scrollback.go:47)）なので、窓ごとに別ファイルになるのは
  自動で成立する。**壊れるのは総量上限の方**:
  `enforceScrollbackLimit(dir, limit, keep, …)`（[scrollback.go:200](../../scrollback.go:200)）は
  「今書いているファイル」を `keep` 1つしか守らない。窓Bがセッションを開いた瞬間に、
  **走行中の窓Aのファイルを古い順の巻き添えで消しうる**。`keep` を生存中の全 sid の
  集合に広げる（窓が1つのときの挙動は変わらない）
- **ADR-0004 は Decision 1/2 を改訂**（グローバル1組 → 窓ごと）。Decision 3/4/5 は不変
- **ADR-0005 は Decision 1 を拡張**（1つの締め → 窓ごとの締め + アプリ全体の待ち合わせ）
- **ADR-0006 / ADR-0007 / ADR-0008 に思想上の変更はない**。ADR-0007 は作業ディレクトリの
  出所が、ADR-0008 は帯の置き場が、それぞれ窓のスコープへ下がるだけ
- **本体 ADR-0050 への依存**: 隔離プロトコルが無い状態で四分割を出すと、同一リポの
  2窓が汚染した経験を台帳に積む。**実装順序は本体が先**（実装フェーズ参照）
- **索引**: `README.md` のADR索引へ追加済み（2026-07-26 承諾時）

## 実装の記録（2026-07-26）: Phase 1 — 窓ごとの状態への切り出し

**UI は1窓のまま、振る舞いを変えずに配線だけを窓ごとにした。** これが Phase 1 の
完了条件そのものである。

```text
frontend/src/App.tsx          682 → 286 行
frontend/src/useChatSession.ts       410 行（新規）
```

- **フロント**: `messages` / `openTurnIdRef` / `boundaryRef` / `closingRef` /
  `activityRef` / `pendingDecidedRef` / `pendingBlocksRef` を
  `useChatSession(paneId, onLedgerChange)` へ移した。App に残ったのは Tomo 一匹に
  属するもの（ヘッダ・成長・姿・Usage・セッション一覧・gui.json）だけで、
  **Decision 1 の「分割するもの / しないもの」の線がそのままファイル境界になった**
- **Go**: `proc *chatProc` → `procs map[string]*chatProc`。`SendLine` / `EndTask` は
  第1引数に pane を取る。`beforeClose` は生きている窓すべてへ `/exit` を送り、
  1つでも送れたら閉窓を差し止める。`shutdown` は全窓を回収するが、
  **猶予は窓ごとに数え直さない** — 人が待つのは1回で、窓が4つあるからといって
  4倍待たされる理由が無い
- **イベント**: `chat:out` / `chat:exit` に `pane` を足し、`chat:view` は
  `{pane, event}` の封筒にした。本体の view オブジェクトに `pane` を混ぜないのは、
  本体 ADR-0032 の契約が「消費者は未知フィールドを無視せよ」であって
  「ハーネスが足してよい」ではないから — 本体がいつか `pane` を名乗ったときに
  黙って衝突する

実装で分かったこと:

- **`--view ndjson` の封筒化がテストに出た**。`chat:view` の payload 形を掴んでいた
  Go 側テスト4箇所が落ち、正しく捕まえた。既存テストが契約の変更を検出したという
  意味では、落ちたこと自体が期待どおり
- `frontend/wailsjs/` の生成バインディングは手で更新した（`wails dev` が
  再生成するが、それを待つとビルドが通らない）

検証（`.claude/skills/verify` の手順・使い捨て `TOMOBIT_DB`・実LLM課金なし）:

```text
PASS  view イベントがターン枠として描かれる
PASS  markdown が描画される / ツール行が出る
PASS  他の窓宛は混ざらない          ← 新しい経路の要
PASS  送信で待ちが立つ / ready で待ちが降りる
PASS  await の note が会話面に出る / 空送信が許される
PASS  app:closing で締めダイアログが立つ
PASS  他の窓の exit で締めが解けない  ← 同上
console errors: なし
```

## 実装の記録（2026-07-26）: Phase 2〜4

### Phase 2 / 3 — 分割と、窓ごとの働く場所

同日に通した（gui.json の窓配列が両方の土台になるので、分けて入れる方が危ない）。

- **窓は React のコンポーネント**（`ChatPaneHost`）。フックは呼ぶ順序が固定で
  なければならず、App の中でループして `useChatSession` を呼ぶことはできない。
  窓を1コンポーネントにすると**その制約が設計と一致する** — 窓が生まれたり
  消えたりすることは、会話が生まれたり消えたりすることそのものである
- **`gui.json` に `panes`**（id / working_dir / read_dirs）。キー無しの旧構成は
  `PaneList` が上位の `working_dir` から1窓を合成する — 既存の設定が黙って
  空の画面になることは無く、保存されるまで1バイトも書かない
- **窓の生死は Go が持つ**（`AddPane` / `ClosePane` / `GetPanes`）。窓を閉じる=
  セッションを区切る（Decision 4）なので、締めを走らせられる側が正本を持つのが筋
- **最後の1窓は閉じない**。会話面が0個の GUI はただ壊れて見える
- **新しい窓は場所を継がない**。直前の窓の場所を引き継ぐと、同じ場所で2つ動く
  構成が既定になる — Decision 6 が事実として言う羽目になる状態を、既定で作りに
  行かない
- 3窓のときは1つ目を左に通しで置いた（実装時ノブ）。余りセルを空白で残すより、
  最初に開いた窓を広く使える方が実務に合う

### Phase 4 — 資源の調停: 3項目のうち、作るものは1つだった

ADR は「実運用で困った順に、先回りして作らない」と書いた。着手して分かったのは、
**3項目の住所がGUIではなかった**ことである。

**① 好奇心予算 — 作るものは無かった。** `BudgetWindowMs` は共有台帳の
`tomo.asked` を読む**導出View**（本体 ADR-0007 Decision 3）なので、窓が何個あろうと
**既に1つを食い合っている**。Decision 5 が「人ごと」と書いた姿は、実装を1行も
足さずに成立していた。残るのはキュー化（1つだけ質問できて他が無言になる体験）で、
これは体験の問題であって資源の問題ではない — **困ってから作る**

**② 知覚の逐次化 — これだけ作った（本体側）。** 窓が4つあれば境界も4つ同時に
来うるが、ローカルのモデルは1つしかない。`facelock` に `AcquireWithin` を足し、
`perceiveBestEffort` が機械に1本の枠（`~/.tomobit/perceive.lock`）を取ってから走る。
**待ちきれなければ知覚を諦める** — セッションは pending のまま残り
`tomobit perceive` が後で消化する。境界を人質に取らないための降り方で、
モデルが落ちている時の既存の劣化と同じ結末になる（順序を落としても台帳は嘘を
つかない — 本体 ADR-0041）

**③ 並走ゲートの本数表示 — 本体の論点。** ゲートは本体 `split.go` にあり、
生存セッションを数えるのは本体 `presence`。GUI から足せるものが無い。
しかも本体 ADR-0028 の計測レビュー（2026-07-26）が明らかにしたとおり、
**非TTY が入口である以上ゲートは構造的に立たない** — 表示を足す前に、
GUI から並走を許可する経路そのものが要る。**別の論点として残す**

### あわせて塞いだ実バグ

起草時に Consequences へ書いた `enforceScrollbackLimit` の穴（走行中のファイルを
1つしか守らない）は、窓が実在するようになった今、現実の不具合になった。

## 追記（2026-07-26）: GUI には権限の配線が無い

実課金の並走で判明した。隔離の指示は正しく届いていた — 両方のモデルが
「git worktree で隔離して作業を行います」と言った。その直後にこうなった:

> ファイル操作と git コマンドの実行に permission が必要です。
> 以下を実行する許可をいただけますか？

`composeChatArgs`（[chat.go](../../chat.go)）は `--permission-mode` を渡していない。
本体の既定は `""` で、実測（本体 ADR-0050）のとおり headless では書き込みが
拒否される。**GUI から起動した Provider は、ファイルを書く仕事ができない。**

正直に言えば**これは本ADRが作った穴ではない**。隔離の前から、GUI 経由の
編集タスクは同じ壁に当たっていたはずである。隔離プロトコルは、それを
**作業の1歩目**へ前倒しにして見えるようにしただけである。

2つの論点が開いた:

1. **GUI が権限モードを渡すか。** ADR-0007（実行ボタン）が「実行経路は
   便利さのために既定で開けてよい種類の口ではない」と切った領域そのもの。
   既定で `bypassPermissions` を渡すのは、その判断を無言で覆すことになる。
   設定の明示ノブにするか、権限要求を画面の問いへ翻訳するか — **別ADRの論点**
2. **プロトコル文が「許可が無い」場合を想定していない**（本体 ADR-0050）。
   Decision 2 は `isolated:false` を「隔離できない現場」のために用意したが、
   権限で止まったモデルは**宣言せずに人へ質問した**。結果 `task.workspace` は
   0件で、台帳には「隔離を試みたが権限で止まった」が1バイトも残らない。
   プロトコル文に「許可が得られない場合も false で宣言せよ」を足すのが
   実装時ノブの筆頭になる

> **どちらも解決済み（2026-07-27）**: 論点1は [ADR-0013](ADR-0013-permission-is-shown-before-it-is-granted.md) —
> GUI は権限モードを渡さず、本体が流す権限要求を問いのモーダルへ翻訳する。
> 論点2は本体 [ADR-0053](https://github.com/Rererr/tomobit/blob/main/docs/decisions/ADR-0053-permission-is-asked.md)
> が引き取り、既定を `auto` にしたうえで許可を人に訊く経路そのものを作った。
