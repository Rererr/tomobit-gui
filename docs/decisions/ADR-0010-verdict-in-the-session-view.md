## Context

本体 ADR-0055 が第2層 `user.verdict` に書き手を2つ与えた。境界で矛盾が出た日に
だけ立つ問いと、閉じたタスクへの `tomobit verdict <sid> up|down|clear` である。

同ADRは正直な注記を1つ残している:

> 書き手Bの入口は sid で、CLI では遠い。GUI のタスク一覧に 👍/👎 が並んで完成、
> という見立てを隠さない

本ADRがその Phase 3 である。**器官は本体に揃っているので、ここで決めるのは
「どこに置くか」だけ**である。

第2層は ADR-0003（本体）が「気が向いた時」と書いた任意の器官で、境界に常設の
問いを足さないことが設計の一部だった。GUI 側でもそこは同じで、**開くたびに
判定を迫る形にはしない。**

---

## Decision 1: 置くのは詳細、印は一覧

判定のボタンは**過去セッションの詳細**（SessionPane）のヘッダ直下に置く。
サイドバーの一覧には**いま置かれている判定の印**（👍 / 👎）だけを出す。

```text
サイドバー一覧   「7/26 ・3ターン ・👍」        ← 思い出すための印
セッション詳細   [👍 よかった] [👎 だめだった] [取り消す]   ← 置く場所
```

理由:

- **判定は「開いた人」の行為である。** 一覧に3つのボタンを並べると、スクロール
  しているだけの人の目の前に選択肢が常時ある。「気が向いた時」の器官を、
  見るたびに迫る器官へ変えてしまう
- **一覧は既に「例外だけ書く」規律を持っている**（`sessionMeta` は finished を
  書かず、進行中・中止・learning だけ注記する）。判定が置かれているのは例外
  なので、この規律にそのまま乗る
- **どれを判定したか思い出せることには価値がある。** 印が無いと、同じ
  セッションを何度も開いて確かめることになる

## Decision 2: 誰を判定できるかは、GUI が決めない

本体は4つを断る — 中断・未終了・分割の子・amend済み。**その規則を GUI に
写さない。** ボタンは常に出し、断られたら本体の文言をそのまま出す。

これは ADR-0001 Decision 1（新しい真実を作らない）と、本体 ADR-0033 が
forget/amend について書いた「JSONやproviderの検証はCLIが唯一の検証者 —
GUIで再実装すると本体の閉集合とドリフトする」の、同じ線である。

判定の可否は本体の Decision であって画面の都合ではない。ここで先回りすると、
本体が規則を変えた日に GUI が黙って古い規則で描き続ける。

**断り文がそのまま出せる形になっているのが効いている。** 本体の拒否メッセージは
行き先まで書いてある:

```text
verdict: k は分割の子で、経験を持たない（ADR-0054）。親の p を判定する
verdict: a は amend 済み（人間の知覚は最終知覚 — ADR-0033）。判定も変えるなら amend --outcome を使う
```

GUI が「判定できません」と要約したら、この行き先が消える。

### 却下: `status` を見てボタンを隠す

一覧も詳細も `status`（"finished" / "cancelled" / "open"）を既に持っているので、
中断と未終了の2つだけなら GUI 側で隠せる。却下する理由は、**4つのうち2つだけ
隠すのは一貫していない**から — 分割の子と amend済みでは押せてしまうので、
「押せるボタンは通る」という期待をどのみち作れない。それなら全部押させて、
断り文を出す方が規則が1つで済む。

## Decision 3: 押した通りには描かない — 台帳が正

ボタンの押下状態はローカルに持たず、**判定のあと台帳を読み直して描く**。

本体は断ることがあるので、押した通りに描くと嘘になりうる。同じ理由で、
判定が通ったら一覧も読み直す（印を追随させる）。

## Decision 4: 確認ゲートは置かない

forget が二段確認を要るのは不可逆だからである（ADR-0006 / 本体 ADR-0033）。
判定は `clear` で取り消せる。可逆な操作に儀式を足さない。

かわりに、**何が起きるかは1行で見せる**:

> 判定はテスト結果や締めの答えより強く効く。取り消せば元の層に戻る

本体 ADR-0053 が許可モーダルに再実行の費用を書いたのと同じ理由で、
効果を隠さない。これは GUI の評価ではなく、本体の `OutcomeWeight` の導出順序を
そのまま述べたものである — 第2層は最初に読まれる層である。

## Decision 5: 未知の語は印を出さない

`user.verdict` の payload が将来増えたとき、GUI が知らない語を 👍 か 👎 の
どちらかへ寄せて描くと嘘になる。**知らない語は「まだ何も置かれていない」**
として扱う（ADR-0032 の消費者規律）。`clear` も同じ扱いで印が消える。

---

## Consequences

- `SessionDigest` / `SessionDetail` に `verdict` が増える。GUI は
  `user.verdict` を読むだけで、最後が勝つ規則も本体の `parseDeterministic` と
  同じ（最後に代入したものが残る）
- **新しいバインディングは1つ**: `SetVerdict(sessionID, verdict)` →
  `tomobit verdict <sid> <word>`。forget/amend と同じ `runWriteVerb` を通る
  ので、成功時は本体の1行サマリ、失敗時は本体の stderr がそのまま人へ届く
- **判定はダイジェストの行にならない。** 会話の出来事ではないので、本文の
  時系列には混ぜない（ヘッダの帯にだけ出る）
- 判定のたびに `GetSessions` を読み直す。既存の `refreshLedgerViews` を使うので
  新しい経路は増えない
- **本体の書き手A（境界の矛盾フォローアップ）は GUI からも通る。** あれは
  ADR-0051 と同じ境界チャネルに乗るので、view ストリームの note として
  会話面に出て、入力欄から答えられる — 本ADRの範囲外だが、両方の書き手が
  GUI から届くことになる

## 実装時ノブ

- 一覧の印の出し方（現状: メタ行の末尾に絵文字。判定の多い台帳で見づらければ
  行頭へ移す）
- 詳細の帯の位置（現状: ヘッダ直下・本文の前。本文を読んでから判定する動線なら
  末尾の方が自然かもしれない — 実際に使ってから）

  （本体の実測では訊かれた26回中8回が「まだ言えない」だった。受け皿はできたが、
  それを**見つける**口はまだ無い）
