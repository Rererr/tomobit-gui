---

## Context

本体 ADR-0056 が並走ゲートを撤回し、独立宣言された群が**訊かずに並走する**ように
なった。同ADRは自分が作った劣化を隠さずに書いている:

> 並走の子の出力は、view ストリームでは note 行として届く。（…）どのサブタスクの
> 発言かは読めるが、型付きの吹き出しにはならない — 逐次の子が持つ view フレームを
> 並走の子は持たない。**これは既知の劣化であり、隠さない**

理由は本体側の型にあった。`ndjsonView` の出すイベントに**どの子が言ったかを載せる
場所が無く**、K本が同時に emit するとフレームが混ざる。だから並走の子だけが端末用の
`[2:claude-code] …` ラベルを経由して note になっていた。

本体 ADR-0032 に `sub` / `sub_total` が足され、その前提が消えた。本ADRは
**GUI 側で何をどう描くか**を決める。

---

## Decision 1: 子は「もう一人の Tomo」ではなく、同じ Tomo の内訳として並べる

並走する子は、会話の流れに**縦に並ぶ通常のターン枠**として描く。左に細い帯、
ヘッダに「サブタスク 2/3」のチップ。それだけである。

```text
Tomo  claude-code
  3つに分けて並走します。                    0.9s · $0.0200

  -- group 1/1: 3本を並走（概算 $0.62 …）--

│ Tomo  サブタスク 1/3  claude-code
│   csvstat: … 統計を実装した                5.2s · $0.2100
│ Tomo  サブタスク 2/3  claude-code
│   httpecho: サーバを実装した                4.1s · $0.1900
│ Tomo  サブタスク 3/3  claude-code
│   wordfreq: 頻度を数えた                   6.0s · $0.1800
```

**却下したのは、並走を「同時性」として見せる形**（横に並べる、列にする、
進行バーを3本立てる）である。理由は本体 ADR-0054 の原則そのもの —
**子は親タスクの内訳であって、独立した発注ではない**。同時に走っていることは
実行の都合で、読む人にとっての意味は「1つの仕事が3つに分かれた」である。
横に並べると、ADR-0009 が窓について守った「Tomo は一匹」の線が、こんどは
分割の軸で崩れる。

チップと帯だけに留めたのも同じ理由。**見分けはつくが、別の生き物には見えない。**

## Decision 2: 当て先は番号でしか決まらない — 並び順で決めない

到着順は入れ違う。それが並走である。だから本文・ツール・エラー・終了のいずれも、
**`sub` を見て自分の枠へ入れる**。`sub` を持たない行は会話そのもののターンへ。

閉じるのも自分の枠だけである。**先に終わった子の `turn.finished` が全員を
閉じてはいけない** — これは実装前に持っていた「いま開いている枠」1つの形が
そのまま持っていた壊れ方で、まだ走っている子の本文が行き場を失う。

### 当て先の規則は1つに閉じる（`SubtaskFrames`）

ライブ（`useChatSession`）と過去の再生（`viewFold`）は別のリデューサで、枠の実体も
違う（前者はメッセージ id、後者は配列 index）。**規則だけを共有する**ために、
当て先の決め方を型引数つきの小さなクラスに出した。

これは「テストのための抽出」ではない — 同じ規則が2箇所にあると、片方だけ直した日に
ライブと再生の見え方が割れる。ADR-0003 Decision 1 が「過去の再生はライブと同じ
構造化描画」と決めた線を、コードの形で保つ。

（副次的に、このリポジトリでユニットテストできるモジュール＝ランタイムの import を
持たない葉、という制約にも収まる。`viewFold` は `budgetToolResult` などを実行時に
呼ぶので `node --test` から読めない。）

## Decision 3: サブタスクの枠にユーザー発話を差し込まない

`viewFold` は台帳の intent を `n` で引いて「You」を差し込む（過去セッションの
全文復元）。**サブタスクの枠には差し込まない。** あれは Provider が書いた内訳の
指示文であって、人が言った言葉ではない。差し込むと、頼んでもいないことを
頼んだように見える。

## Decision 4: 枠が無い行を捨てない

`turn.started` より先に本文が来たら（本体が落とした・順序が入れ違った）、
番号だけ持った枠を開いて受ける。**本文が消えるより、n や provider が空の枠が
1つ増える方が正直である** — `appendBlocksTo` が既に同じ判断をしている。

---

## Consequences

- `TurnMessage` に `sub` / `subTotal` が増える。会話そのもののターンは持たない
- 溜め場（`pendingBlocksRef`）が**枠の id ごと**に分かれる。並走中は宛先が同時に
  複数あり、1本の配列に混ぜると隣の子の本文が自分の枠へ流れ込む。
  フレーム1回のフラッシュという性質は保つ（複製は宛先の数だけで、到着件数には
  比例しない — 2026-07-26 の応答停止の修正が守ったもの）
- 本体の `[n:provider]` ラベルは view に一切来なくなる。あれは共有端末のための
  レイアウトで、構造化された読み手には意味を持たない
- 未知のキーを無視する古い GUI は壊れない（本体 ADR-0032 Decision 1 の前方互換）

## 実測（2026-07-27・実UI・LLM課金ゼロ）

`window.runtime.EventsEmit("chat:view", …)` で、本体が実際に出す形の
**行が入れ違う3本**を流した（verify skill の documented なゼロコスト経路）。

```text
Tomoの枠: 4
  (会話のターン)  | 3つに分けて並走します。                | 0.9s · $0.0200
  サブタスク 1/3  | csvstat: / Write · … / 統計を実装した  | 5.2s · $0.2100
  サブタスク 2/3  | httpecho: サーバを実装した             | 4.1s · $0.1900
  サブタスク 3/3  | wordfreq: 頻度を数えた                 | 6.0s · $0.1800
```

- 入れ違って届いた本文が、**1行も混ざらずに**それぞれの枠へ入った
- 先に終わった sub=2 の `turn.finished` が、まだ走っている sub=1 / 3 を閉じなかった
- 会話そのもののターンはチップを持たず、巻き込まれもしなかった
- 新規のコンソールエラー0（起動時の既知ノイズのみ）

---

## 残っていること

- **実 Provider の並走を GUI で目視していない。** 本体側は同日 opus で3本の
  並走を実測しているが（ADR-0056 実測）、そのときは view フレームがまだ無かった。
  次に実分割が起きたときが最初の実物になる
- 並走中の待ち表示（ADR-0008 の帯）は「実行中」1本のまま。K本走っていることを
  帯が言うかは決めていない — 枠の側で見えているので、当面は足さない
