## Context

ADR-0009 の追記（2026-07-26）が、実課金の並走で見つけた穴から2つの論点を開き、
どちらも「別ADRの論点」として残した。

論点2（隔離プロトコル文が「許可が無い」場合を想定していない）は本体の領分で、
本体 ADR-0050 / ADR-0053 が引き取った。**残った論点1に本ADRが答える。**

> **GUI が権限モードを渡すか。** ADR-0007（実行ボタン）が「実行経路は
> 便利さのために既定で開けてよい種類の口ではない」と切った領域そのもの。
> 既定で `bypassPermissions` を渡すのは、その判断を無言で覆すことになる。
> 設定の明示ノブにするか、権限要求を画面の問いへ翻訳するか

本体 ADR-0053 は後者を選んだ。既定を `auto` にしたうえで、Provider の権限要求を
`{"type":"permission", "await":true, ...}` として `chat --view ndjson` に流す。
GUI に残るのは**その行をどう見せ、どう答えを返すか**だけになった。

## Decision 1: GUI は権限モードを渡さない

`composeChatArgs`（[chat.go](../../chat.go)）に `--permission-mode` を積まない。
本体の既定（`auto`、本体 ADR-0053 Decision 1）に委ねる。

これで ADR-0007 が切った線に触らずに済む。GUI が `open` を渡す道は、あの判断を
無言で覆すことになる。**止まったら訊く**なら、そもそも開けておく必要が無い。

`--provider` を常に明示で積むのとは非対称だが、理由がある。provider は
`gui.json` が持つ **GUI 側の設定**で、渡さなければ GUI が持っている値が捨てられる
（`composeChatArgs` のコメントが言う「既定が変わったとき GUI の挙動が無言で
変わる」はこの状況を指す）。権限モードについて **GUI は値を持たない**。
持っていない値を明示する形は作れない。

却下した対案:

- **`gui.json` に権限モードのノブを足す**: 「原則 auto、止まったら訊く」は本体の
  方針で、GUI に別の口を作れば2箇所で決まる。要るようになってから足せばよい
- **既定で `open` を渡す**: 上記のとおり ADR-0007 の否定。本体 ADR-0053 も
  所有者の方針として明示的に退けた道である

## Decision 2: モーダルは形だけを持つ。語彙は1語も発明しない

本体から届くのは、この1行だけである:

```json
{"type":"permission","await":true,
 "text":"Edit の使用を許可する? [1=許可する / Enter=許可しない]",
 "tools":[{"tool":"Edit","detail":"/tmp/x.go"}]}
```

モーダルの中身は**すべてこの行から取り出す**:

| 画面に出るもの | 出どころ |
|---|---|
| `Edit` / `/tmp/x.go`（何を許すのか） | `tools[]` をそのまま |
| 「Edit の使用を許可する?」（問いの文） | `text` から角括弧を除いた部分 |
| ボタンの文字「許可する」「許可しない」 | 角括弧の `1=許可する` の**右**側 |
| 押したとき送る文字列 `1` / 空文字 | 角括弧の**左**側（`Enter` は空文字＝本体の無信号経路） |

したがって GUI のコードには「許可する」という文字列も、道具の名前の一覧も、
返事の組み立ても**書かれていない**。GUI が持つのは背景を覆う板・道具を並べる
リスト・ボタンを並べる箱という**形だけ**である。これが「語彙を持たない」の中身で、
ADR-0005 Decision 2 が締めの質問について引いた線がそのまま当たっている。

この決定が具体的に禁じるのは2つ:

- **文面から種類を当てない。** 判定は `ev.type === "permission"` で行う。
  「`text` に『許可』が入っていたら権限の問い」と書いた瞬間、本体が文言を
  「Edit の使用を認めますか?」に変えた日に GUI は黙ってモーダルを出さなくなる。
  **壊れたことに誰も気づけない形**になる
- **選択肢が読めないとき、自前のボタンを作らない。** 作れば、押したときに送られる
  文字列が本体の期待するものと食い違い、**本体には意味不明な入力が届く**。
  ここは Decision 3 の落ち先へ倒す

新しい判断ではなく、既にある線を当てただけである。[boundaryChoices.ts](../../frontend/src/boundaryChoices.ts)
の冒頭が締めの質問について書いた理由が、そのまま権限の問いにも成り立つ —
GUI が選択肢の一覧を持てば、**本体が語彙を足した日に GUI が黙って古い選択肢を
出し続ける**。

## Decision 3: 読めない形は、モーダルにせず会話面へ落とす

`tools` が無い・空・選択肢が読めない — このいずれでも `null` を返し、モーダルは
出さない。かわりに問いは会話面の1行（`await`）として残り、**人は入力欄から
答えられる**。

**GUI が読めないことと、人が答えられないことは別**である。形を作れないときに
沈黙すると、答えを待っているターンが画面から消える。

## Decision 4: 何を許すのかを見せてから許可を取る

ADR-0007 の作法を継ぐ。あちらが「走る全文と作業ディレクトリを見せる帯」を開いた
のと同じ理由で、道具の名前と、それが触ろうとしたものを並べてから選択肢を出す。
`detail` は本体が要約した1行で、無いこともある — **道具の名前だけでも問いとしては
成立する**（本体 ADR-0053 Decision 3）。

- 初期フォーカスは `preventScroll: true` で当てる。指定しないと道具一覧が長いとき
  にダイアログが許可ボタンまで自動スクロールし、**押す前に「何を許すのか」が
  視野から消える**（実測: `scrollTop` 282 で Tool 1〜6 が不可視）。作法をブラウザの
  既定挙動が壊す形だったので、実測してから塞いだ
- **再実行の費用は隠さない**。許可はその場で続行させるものではなく、やり直させる
  ものでトークンはもう一度かかる（本体 ADR-0053 Decision 2）。この文面も本体が書く

## Consequences

- 権限の問いのために**新しい経路を作らない**。`chat --view ndjson` の既存の
  view 契約に1つ `type` が増えるだけで、Go 側の配線は変わらない
- **Provider によって体験が違う**ことは GUI では吸収できない。codex には道具ごとの
  許可を持つ機構が無く、許可の問いそのものが立たない（本体 ADR-0053 Consequences）。
  GUI が差を埋めようとすれば、そこで語彙を発明することになる
- 本体が権限の文面や選択肢を変えても GUI は追随不要。逆に、本体が `type` を
  変えれば GUI は静かにモーダルを出さなくなる（Decision 3 の落ち先へ倒れるので、
  問い自体は会話面に残る）
- 本体で `control_request` が使える claude build に切り替わると、本体 ADR-0053
  Decision 2（許可 → 再実行）が差し替えになる。そのとき GUI 側で変わるのは
  文面だけで、Decision 2〜4 はそのまま立つ
