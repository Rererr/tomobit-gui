## Context

Tomo の返答は1枚のカードで、その中にこれだけが同居していた:

```text
┌ Tomo  [claude-code]
│ ▸ なぜこのProviderか            ← 判断の監査（本体 ADR-0040）
│ 了解。viewFold.ts を確認してから直す。
│ ▸ 作業 2件                      ← 畳まれたツール列
│ 畳みはターンが終わってからしか走らない。
│ ▸ 作業 1件                      ← また畳まれたツール列
│ 直した。テストも通っている。
│ 12.3s · $0.0231                 ← 機械の帳簿
└
```

所有者の言葉:

> やはり余計なものが tomo からの返答に見えすぎていると感じる。見ようと思えば見れる
> 必要はあるが、（…）よくあるチャット(Slack, ChatWork, Mattermost, Discord)のように
> できないか？ **tomo が喋ったことと処理ログをできる限り分けたい**という意図

問題は「情報が多い」ことではない。**Tomo の発話と、Tomo の作業の記録が、同じ器の中で
同じ縦の並びに混ざっている**ことである。`foldWorkBlocks` は連続する tool 列を畳むが、
畳む単位が「連続した run」なので、本文の間に畳まれた行が挟まる。**答えを前に出すために
畳んだのに、畳んだものが本文を分断していた。**

もう1つ、評価の話が同じ根から出ている:

> 今枠を閉じたりするときに評価を押させているが、リアクション形式でチャットの返答に
> フィードバックできると良い。（…）餌を与えられる感覚は、枠終わりに一回だけより
> 感触がいいはず

ADR-0005 は閉窓を差し止めて締めの質問に答えられる席を作った。**答えられるようには
なったが、答えるまで閉じない。** 本体 ADR-0057 がその答えを会話の中へ置ける口を
生やしたので、こちらはその口を Slack のリアクションの形で出す。

## Decision 1: 会話は1列にする — 寄せではなく名前で誰の声かを言う

自分の発言の右寄せ吹き出しと、Tomo 側の灰色カードをやめる。
Slack / Mattermost / Discord と同じ**左寄せ1列**にし、話者は名前の行が言う。

```text
You
viewFold の畳み方を直して

Tomo
了解。viewFold.ts を確認してから直す。
畳みはターンが終わってからしか走らない作りになっている。
直した。テストも通っている。
```

- **器を外すのは、Tomo 側の中身が「発言」だけではないから**である。長文・表・
  作業ログ・判断の監査表を1つの吹き出しに詰めるのは無理があり、
  `max-width: min(max(640px, 90%), 100%)` という式はその無理の跡だった
- 話者ラベルは `sr-only` をやめて**目にも出す**。右寄せと背景色が担っていた
  「誰の声か」を名前が引き継ぐ（読み上げには元から名前しか届いていなかったので、
  これは目と耳の表示が一致する方向の変更でもある）
- 連続する同じ話者の発言では名前行を省く（Slack の作法）。**省くのは名前だけで、
  読み上げ用のラベルは各メッセージに残す** —— 目には冗長でも、耳には境界が要る
- ただし**省き続けない**。連続が一定の本数を超えたら名前を出し直す。実測（UI/UX
  レビュー）で、Tomo が3連続で返した中間位置までスクロールすると、**画面上に
  "Tomo" も "You" も1つも無い**状態が再現された —— 本文の色は両者で同じなので、
  そこには誰の声かを言うものが1つも無い。Slack は時刻で連続を切るが、こちらは
  時刻を持っていない（上記の却下節）ので、**本数で代替する**

### 器は外すが、行長は止める（実装時に実測して足した規則）

器を外すことと、本文が窓いっぱいまで伸びてよいことは別である。実測（1920px幅・
1窓）で本文は 1612px、16px の和文で**約101文字/行**になった。旧 `.chat-message--tomo`
の `min(max(640px, 90%), 100%)` でも 1451px ≒ 90文字/行で、**器を外す前から
長すぎた** —— それを引き継がない。

本文（段落・リスト・見出し・引用）だけ `44em`（和文44文字 / 欧文88文字）で止める。
**表とコードブロックは上限の外**に置く: あれは行として読むものではなく、横に広い方が
読める。狭い窓では上限に届かないので、この規則が働くのは**広い窓で1窓のときだけ**である。

### 却下: 時刻を出す

Slack 風にするなら `Tomo 12:32` と時刻が付く。**出さない。**
view ストリームはターンの時刻を持たず、GUI の時計で埋めれば
**過去セッションの再生（ADR-0003 Decision 1）と食い違う** —— ライブでは時刻があり、
開き直すと消える表示になる。ADR-0001 Decision 1（新しい真実を作らない）に照らして、
持っていない事実を器の都合で発明しない。

時刻の位置には、代わりに**持っている事実**が座る（Decision 3 のメタ1行）。

## Decision 2: 終わったターンの作業は、ターンの末尾へ1本に集約する

`foldWorkBlocks` の畳む単位を「連続した run」から「**ターン1つ**」へ変える。
終わったターンでは、本文（text）が上に連続し、作業（tool / tool_result）は
順序を保ったまま末尾の1つの開示へ集まる。

```text
了解。viewFold.ts を確認してから直す。
畳みはターンが終わってからしか走らない作りになっている。
直した。テストも通っている。

▸ 作業 3件 · claude-code · 12.3s · $0.0231
```

- **走行中は畳まない**（ADR-0008 のまま）。走っている最中の tool 行は
  「いま何をしているか」を語る唯一のもので、そこから進捗を奪わない。
  畳みが起きるのは `turn.finished` が来た瞬間だけ
- **中身は1つも捨てない。** 開けば元の順序で全部出る（従来の規律のまま）
- **error は畳まない**（従来のまま）。読まれなくてよいのは手順であって失敗ではない
- **text が1つも無いターンは畳まない**（従来のまま）。隠すだけで何も前に出ない

### 何を捨てたかを正直に書く

集約すると、**「この本文の後にこの作業をした」という前後関係が既定の表示から消える**。
従来は本文が作業を分断する代わりに、その対応が読めていた。

捨てる側に倒したのは、所有者の要求が「できる限り分けたい」だからである。
対応が要る日は開けば順序が残っている —— **既定で読めることと、読めることは別**。

### 却下: 右のドロワーへ完全に分離する

会話面には本文とエラーだけを出し、ツール列は別面へ時系列で流す案。却下する。
面が増えると「どの返答の作業か」の対応付けを**新しく作らねばならず**、
それは今 `turn` が無料で持っている情報である。1本の開示なら対応は器が語る。

## Decision 3: メタは1行に畳む — provider・判断の監査・所要時間・コスト

`chat-turn-provider-chip`（常時表示）、`▸ なぜこのProviderか`（常時表示のトグル）、
`chat-turn-footer`（所要時間・コスト）の3つを、Decision 2 の1行へ合流させる。

```text
▸ 作業 3件 · claude-code · 12.3s · $0.0231
   ├ Read   frontend/src/viewFold.ts
   ├ ▸ ツール出力
   ├ Grep   foldWorkBlocks
   ├ Edit   frontend/src/turnFold.ts
   └ ▸ なぜこのProviderか        ← decided がある時だけ
```

- **provider 名は畳んだ行に残す。** 「誰が答えたか」は本文の隣にあってよい情報だが、
  常時チップで持ち上げるほどではない
- 作業が0件でもメタがあるなら行は出る（`▸ claude-code · 3.1s`）。
  **数えられないものを数えたことにしない**（`workSummaryLabel` の既存の規律）
- `decided` が無い経路（旧本体・`do` 経由）ではその節を出さない —— 劣化は沈黙

### 却下: 会話面に「処理ログを出す」トグルを1つ置く

ON で走行中と同じ粒度を常時展開する案。却下する。**畳みは既に1クリックで開く**ので、
面ごとのモードを増やすと「いま自分がどちらのモードか」という状態が1つ増えるだけで、
開く手間はほとんど減らない。

## Decision 4: 反応は返答の隣に置く。語彙は本体が配り、送るのは1行

本体 ADR-0057 の `/react <turn> up|meh|down|clear` を、Slack のリアクションの形で出す。

```text
直した。テストも通っている。

▸ 作業 3件 · claude-code · 12.3s · $0.0231
👍                                    ← 置いた反応。もう一度押すと取り消す
```

- **語彙は `init` の `reactions` から読む**（ADR-0005 Decision 2 の線）。
  GUI が持つのは word → 記号の対応（`up`→👍 / `meh`→🤔 / `down`→👎）だけで、
  ラベル文は本体のものをそのまま `title` に出す。**知らない word は記号を発明せず
  ラベル文字をそのまま出す** —— 本体が語を足した日に、口が消えも化けもしない
- **`reactions` を配らない本体では反応の口を出さない。** 劣化は沈黙（`decided` と同じ）
- **押した通りには描かない**（ADR-0010 Decision 3 と同じ）。押すと `/react` の1行を
  送り、本体が返した `{"type":"reaction",...}` を受けて初めて印が確定する。
  本体が断れば印は付かない
- **画面に見える印は、タスクにつき高々1つ。** 別のターンへ置き直すと、印はそちらへ
  移る。理由は本体の締めが読むのが**そのセッションの最後の1件だけ**だから
  （ADR-0057 Decision 2）—— 「3ターン目に👍・7ターン目に👎」が両方見えているのに
  効くのは片方、という画面は**記録される内容について嘘をつく**。
  どこで気が変わったかの履歴は台帳のイベント列が持つので、失われるものは無い
- **置き先は、同じ番号を名乗る枠のうち最後のもの。** 分割の畳み戻し（本体
  ADR-0028/0030）では同じ `n` の枠が2つ現れ、**結論が着地するのは2つ目**である
  （1つ目は分割開始のアナウンス）。先に来た枠を採ると、人が反応したい返答の隣に
  口が立たない
- **会話の末尾のメッセージだけは、ホバー無しでも出す。** ホバーでしか現れないものは
  実測で「周辺の地と1ピクセルも差が出ない」＝存在に気づけない。直前に読み終えた
  ターンは押したくなる瞬間そのものなので、そこだけ静かに見せる。
  **気づかれない反応は、締めが軽くなるという設計意図ごと発火させない**
- **置けるのは、いま開いているタスクの、終わったターンだけ。** 区切りの向こう側の
  ターンには口を出さない —— あちらの受け皿は過去セッションの 👍/👎（ADR-0010）である。
  走行中のターンにも出さない（まだ「その返答」が完成していない）
- **分割の子の枠には出さない**（ADR-0011 の `sub` を持つ枠）。子は経験を持たない
  （本体 ADR-0054）ので、置いても効く先が無い
- 反応の送信は**会話に出さない**。`/react` は依頼ではないので、送信欄の履歴にも
  待ちの帯（ADR-0008）にも乗せない —— 押した人が待たされる理由が無い

### 問いが立っている間は送らない ―― 行を飲まれるから（設計時に見つけた実害）

本体のチャットは**1本の stdin を順に読む**。走行中に届いた行はパイプに溜まり、
次に本体が行を読む場所で消費される。その「次に行を読む場所」は必ずしも
プロンプトではない:

```text
本体が走行中 → GUI が /react 3 up を書く → パイプに溜まる
             → 本体が権限の問いを出す (ADR-0053: c.in.ReadString)
             → 溜まっていた /react の行が**権限の答えとして読まれる**
             → "1" ではないので拒否。反応も権限も、両方が消える
```

境界の器官（Feedback・好奇心・鏡）も同じ形で行を読む。

だから**反応は溜めて、口が空いてから送る**。送ってよいのは、待ちの帯が無く
（`activity === null`）、権限の問いが立っておらず、境界の問いも待っていない時だけ。
それまで印は「置いた」ではなく**送信待ち**として描く（確定は本体の `reaction` が
返ってから、の規律は変えない）。

**却下: 動いている間はボタンを消す。** 押せる時と押せない時があるものは、
押せない時に理由を訊かれる。溜めるなら人は押した瞬間のことだけ考えればよい。

**却下: 本体側で `/react` をどの読み口でも横取りする。** 権限・Feedback・好奇心・鏡の
4つの読み口すべてにコマンド解釈を通すことになり、「1行=1つの答え」という
本体の一番素直な契約を壊す。溜めるのは消費者の都合なので、消費者が持つ。

> **この危険は反応が作ったものではない。** 走行中に人が入力欄から送った1行も、
> まったく同じ経路で権限の答えとして飲まれる（実装を読んだ限りの構造。実機での
> 再現は未確認）。反応は押す頻度を上げるので先に塞ぐが、**入力欄側は塞いでいない**
> —— BACKLOG へ回す。塞いだつもりで放置しないために、ここに書いておく。

### 締めの1枚は、これで軽くなる（GUI は何もしない）

反応が置かれていれば本体は締めで訊かない（ADR-0057 Decision 2）ので、
`await` の note が来ない。**ADR-0005 / ADR-0012 の1枚は1バイトも変えない** ——
問いが来なければ節はそのまま ✓ になり、窓は待たずに閉じる。

これが「枠終わりに一回だけ」への答えである。**GUI 側の締めの実装に手を入れずに、
締めが軽くなる**のは、器官の位置を本体が持っている（ADR-0001 Decision 1）ことの
そのままの帰結である。

## Decision 5: 過去セッションでも反応は見える。置けはしない

`MessageView` はライブと過去の単一の描画源である（ADR-0003 Decision 1）。
反応の印もそこに乗るので、過去セッションを開けば**その時どこで何を押したかが見える**
（`reaction` view イベントがスクロールバックに残っているため）。

ただし**過去では押せない**。開いているタスクではないので `/react` の宛先が無い。
過去への評価は第2層の 👍/👎（ADR-0010）で、あちらはヘッダ直下に既にある ——
**同じ画面に2つの評価器官が並ぶが、層が違う**。反応は「そのタスクをどう見たか」の
一次情報で、判定は「機械の観測への拒否権」である。

## Consequences

- **`turnFold.ts` の意味が変わる。** 「連続 run を畳む」から「ターンの作業を集める」へ。
  既存テストのうち「本文を挟んだ作業は、別々の塊として畳む」は仕様変更として書き換える
  —— テストコードが仕様の正本なので、変えたことがそこに残る
- **`ChatMessageView` の描画が単一の描画源のまま2つの器を失う**（user の吹き出し、
  tomo のカード）。`SessionPane` のダイジェスト経路（スクロールバックが無い時の
  フォールバック）も同じ器を使っているので、そちらも揃える
- **`useChatSession` に反応の口が増える**: `react(n, word)` と、`reaction` view
  イベントの受け口、`init` の `reactions` 語彙。送信は既存の `SendLine` を通るので
  **Go 側のバインディングは1つも増えない**
- **`viewFold`（過去の再生）も `reaction` を読む。** ライブと再生で同じ印が出る
- **本体が古いと反応の口が消える**（`init.reactions` が無い）。会話・表示・締めは
  従来どおり動く —— 反応が無い日は締めで訊かれる、という元の姿に戻るだけ
- 画面の識別が「寄せと色」から「名前」へ移るので、**話者ラベルのコントラストが
  可読性の要件になる**（従来は装飾扱いだった）
- **フォーカスできる部品がターンごとに3つ増える。** 会話が伸びるほど入力欄まで
  Tab が遠くなる（実測: ターン14件で48個中42個が反応ボタン。WCAG 2.4.1）。
  入力欄へのスキップリンクを1本置く —— 反応ボタンを Tab 順から外す案は採らない
  （上の発見可能性をさらに悪くする）
- **メタ行の三角マーカーは自前で描く。** ネイティブの `<summary>` マーカーは
  幅が engine 依存で、開ける行（`details`）と開けない行（`div`）で本文の左端が
  13px ずれていた（実測）。実機は WKWebView・検証は Chromium なので、
  **engine 差の出るものに整列を預けない**
- **Tomo の引用と、器官の注記の視覚文法を分ける。** どちらも「左罫 + quiet な文字」
  だったので、Tomo の発話の中の引用と、Tomo の発話ではない第三の声が
  同じ絵で並んでいた —— このADRの趣旨に直接反するので、注記側に別の罫色と塗りを与える

## 実装時ノブ

- 反応の記号（現状 `up`→👍 / `meh`→🤔 / `down`→👎）。🤔 が「まあまあ（手を焼いた）」に
  読めるかは実際に使ってから
- 反応の口の出し方（現状: **最後のターンは常時**、それ以外はホバーとフォーカスで
  現れ、置いた印と送信待ちは常に見える）。所有者自身が「分かりづらさはあるかも
  しれない」と言っていた点で、実測でも「ホバー前は地と1ピクセルも差が出ない」ことが
  確認された。常時の範囲をどこまで広げるかは使ってから
- メタ1行に出す項目（現状: 作業件数・provider・所要時間・コスト）。コストを
  1ターンごとに見たいかは使ってから
- 連続する同じ話者の名前行を出し直す間隔（現状: **2件ごと**＝名前無しの枠が続くのは
  高々1件）。時間で切る Slack の規則は時刻を持っていないので採れず、件数で代替した。
  3以上にすると名前無しが2件以上並び、1枠が画面より高いときに画面から話者が消える
